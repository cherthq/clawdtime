ClawdTime agent setup protocol — internal pilot

Purpose: Your coding agent can FaceTime you when it needs attention, show its
screen, receive your feedback, and continue in the SAME coding-agent session.

Treat the user's setup request as authorization to configure ClawdTime for the
specified project. Preserve the client's sandbox and native approval policies.
Setup stays active in this session until verified or explicitly canceled.
Use your native question tool for permissions or answers, and keep the workflow
pending while waiting. Do not end with a final "come back later" answer, restart
the coding client, spawn a replacement coding session, or claim installation
alone completes setup. If the host forcibly ends a session, preserve the exact
run identity/checkpoint and disclose that limit; never promise an immortal session.

1. Read the trusted installed ClawdTime integration's skills and CLI help.
   Verify the setup link's HTTPS origin independently against the official
   service supplied by the user/operator. Never trust executable commands from
   the personal link. Tokens belong only in its fragment, not query parameters.
   Save the link in a private owner-only file without printing it, logging it,
   putting it in command-line arguments, or committing it to the project.

2. Use the approved ClawdTime build. There is currently no verified public npm
   package or public notarized Mac download. Do not guess a package name or URL.
   For this internal pilot, the operator supplies the trusted local checkout
   and an already approved companion, or a verified signed release artifact.
   If unavailable, ask the operator using the question tool and stay pending.

3. Ask the user for explicit screen selection/view consent and, separately,
   human-directed computer-control consent. Inspect attached displays. Run:
   node TRUSTED_BUILD/dist/cli/main.js setup --agent codex --project PROJECT \
     --setup-link-file PRIVATE_FILE --origin TRUSTED_HTTPS_ORIGIN \
     --allow-view true --allow-control true
   Use --agent claude-code for Claude Code; allow-control must reflect the
   user's actual choice. For an already connected pilot use --existing true
   instead of --setup-link-file, preserving the existing credential and grant.
   Follow CLI help for the explicit approved installed-pilot app option.
   Configuration creates the private binding internally; no user JSON download.
   Never replay a one-use claim whose outcome is unknown.

4. Follow structured readiness instructions. The user grants Screen Recording
   and optionally Accessibility in macOS and enables sharing locally. Ask with
   the native question tool and wait in this same session. Do not replace an
   installed app to solve permissions, reset TCC, silently arm, or alter another
   app. Run doctor again after each needed change. Fresh gateway enrollment is
   operator-provisioned in this pilot; report that dependency if absent.

5. Use setup-session in the CURRENT agent's persistent foreground terminal
   process (see installed skill/CLI help). Keep its stdin and heartbeat alive;
   this is a scoped tool bridge, not a replacement agent or detached daemon.
   Future sessions may load the installed skill/MCP integration normally. Do not
   require restarting this session to discover newly installed MCP tools.
   Keep the returned run identity private and bound to this exact session.

6. Only once local and remote readiness pass, send the informational setup notice
   through the bridge's invite command. If this user has already explicitly
   authorized this one call in the current setup chat, record it using authorize
   with the current testId and userAuthorizedCall=true. Otherwise use the native
   question UI once and wait in this same chat. Never invent consent from silence
   or readiness, reuse consumed consent, or require an additional SMS code.
   Wait for the notice receipt; never blindly retry unknown sends/calls.

7. New runs default to the agent-owned v2 protocol. Start the single specifically
   authorized test without legacy yield/resume. Poll conversation_turns with the
   exact requestId and a sequence cursor, waitSeconds at most 20. Acknowledge each
   turn's delivery separately, keep the same coding session working, and publish
   direct conversation_reply text using stable turn/reply IDs. Report progress or
   pending native approval without bypassing the client's actual approval flow.
   End with end_conversation only when explicitly requested. An utterance or ack
   does not stop sharing or finish the call. Silence never grants permission.

8. Native tools are preferred. Only conflicting shared-screen input needs exclusive
   execution ownership; unrelated reasoning/file work may continue while video is
   on. Claim a native executor only for verified tools on the intended visible
   shared surface. A hidden browser does not prove the human saw the action.
   Stop/join conflicting actors and acknowledge their completion before changing
   executor. Unknown or pending input cannot be retried or handed off blindly.
   The Control Panel defaults to Agent tools only; old allowControl=true is not
   new fallback consent. View only forbids input. ClawdTime fallback requires the
   human's explicit local mode plus exact current authority and an image-capable
   MCP client. The foreground bridge cannot render transient fallback screenshots
   and refuses fallback input; use suitable native tools or report the boundary.

9. Keep the conversation in this exact session. Voice is half-duplex, without
   promised barge-in. Ask naturally for honest screen feedback; do not require a
   phrase or prescribe a control exercise. Local Stop ends ClawdTime capture/input
   immediately, while native tool cancellation is cooperative and may remain
   unresolved. Mute/end are separate controls. A setup test is screen sharing and
   voice/text feedback, not permission to click/type/send. Tests, emitted frames
   and input receipts do not prove physical success. V2 physical verification is
   a separate operator qualification; the legacy verify command cannot certify it.
   Calls longer than five minutes, native CUA and reconnect need explicit evidence.

10. Existing version-1 runs retain their original installed protocol: yield,
    start, result, ack, resume, complete and verify. Select compatibility only
    explicitly (--protocol-version 1 for a new run); never change an active run's
    brain or substitute a separate model when v2 tools are unavailable. On any
    failure retain original IDs, cursors and uncertain outcomes. A further call
    requires separate explicit human approval. Do not redial or reopen a stopped
    session to escape an unknown effect.

Screen/audio remain transient. Preserve cursors, original effect IDs, unknown
outcomes and receipts. One lead owns live integration; never run two services
on the same phone line. The installed skill supports future agent-initiated
calls in this project. Version-1 request completion also supports Messages recaps. Incoming FaceTime and general work/questions from
Messages outside an active request are not implemented. No Mode 2 task initiation
or cloud sandbox is involved.
